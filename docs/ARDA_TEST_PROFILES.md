# ARDA test profiles and current baseline

This file is the source of truth for the command line used during AAOS -> AAP/DHU bring-up.

The goal is to stop reconstructing long commands from shell history or old chats. The current baseline lives in the repository root as `config.toml`.

## Current baseline

The current profile intentionally enables only:

- HU-side USB AAP transport through the platform-owned `/dev/usb_accessory` gadget stream
- platform `screenrecord` raw H.264 backend
- SDR-driven 1280x720 / 30 fps selection
- Waveshare 7.9 display geometry profile
- secured platform InputBridge injection over the v54 filesystem UNIX socket

Audio and sensor/VHAL forwarding remain disabled in the baseline. The sensor parser now has an explicit master gate and the v56 Wasmtime VHAL policy engine is configured but is not instantiated until `--sensor-open` is explicitly enabled.

The selected H.264 encoder is currently `c2.android.avc.encoder`. The Pi V4L2 encoder `c2.v4l2.avc.encoder` returned `Encoder failed (err=-38)` and produced zero NAL units in the controlled A/B test.

## USB policy and role

Normal AAP commands do **not** create, rebind, or repair a configfs AOA gadget anymore.

The current AAOS image already owns USB accessory setup through its platform/init USB stack. ARDA only consumes the resulting device-side character stream:

```text
car / DHU = USB host
        ↓ AOA negotiation handled by the platform USB stack
AAOS Pi = USB gadget / Android-device side
        ↓
/dev/usb_accessory
        ↓
arda-senderd = phone-like AAP endpoint
```

This matches the HU-side branch in `aa-proxy-rs`: its car/HU path opens `/dev/usb_accessory` directly. Its separate `nusb`/AOA control-request and bulk-endpoint path is for a **wired Android phone (MD)** attached to the proxy as a USB host. ARDA is replacing that MD/AAP endpoint, so it must not run the phone-side `nusb` accessory-switch path.

Read-only check:

```bash
adb shell /data/local/tmp/arda-senderd usb-accessory-status
```

Expected minimum result:

```text
USB_ACCESSORY_NODE_OK=YES
USB_ACCESSORY_MISC_OK=YES
USB_ACCESSORY_READY=YES
```

`USB_LINK_CONFIGURED=YES` additionally means the UDC currently reports a configured host link.

The old command remains only as a manual/legacy recovery tool for older images:

```bash
adb shell /data/local/tmp/arda-senderd aaos-aoa-gadget --check
```

Do not put `aaos-aoa-gadget` in the normal startup path for the current image.

## Install the current binary and profile

From the repository root on the Mac:

```bash
PI="1000000028c0b59c"

adb -s "$PI" root
adb -s "$PI" wait-for-device

adb -s "$PI" push \
  target/aarch64-linux-android/release/arda-senderd \
  /data/local/tmp/arda-senderd

adb -s "$PI" shell chmod 755 /data/local/tmp/arda-senderd

adb -s "$PI" push \
  config.toml \
  /data/local/tmp/arda-config.toml
```

Certificates are separate runtime secrets and are not stored in this repository. The AAP TLS server expects:

```text
/data/local/tmp/arda-certs/md_cert.pem
/data/local/tmp/arda-certs/md_key.pem
```

## Validate the profile

```bash
adb shell /data/local/tmp/arda-senderd \
  config-check /data/local/tmp/arda-config.toml
```

This prints the CLI arguments generated by the profile. Unknown config keys fail instead of being ignored.

## Start the current baseline

```bash
adb shell /data/local/tmp/arda-senderd aap-run
```

`aap-run` is shorthand for:

```bash
adb shell /data/local/tmp/arda-senderd \
  aap-session-probe \
  --config /data/local/tmp/arda-config.toml
```

Config values are applied first. Explicit CLI flags come after them and therefore override the profile for one A/B run.

Examples:

```bash
# Lower logging for a latency run.
adb shell /data/local/tmp/arda-senderd \
  aap-run \
  --log-level summary

# Temporary TCP fallback/debug path.
adb shell /data/local/tmp/arda-senderd \
  aap-run \
  --transport tcp \
  --addr 0.0.0.0:5277

# Temporary sensor/VHAL A/B without editing config.toml.
adb shell /data/local/tmp/arda-senderd \
  aap-run \
  --sensor-open \
  --sensor-request-all \
  --sensor-max-type 23 \
  --sensor-jsonl /data/local/tmp/arda-sensors.jsonl \
  --sensor-wasm builtin \
  --sensor-forward-vhal \
  --sensor-vhal-min-ms 500
```

## Baseline rationale

### `video.frames = 0`

Zero means unlimited live frames. A previous test command omitted this and the default frame limit stopped video after 30 frames, which looked like a frozen DHU image.

### `input.inject_mode = "bridge"`

The Waveshare setup uses 1280x720 logical AAP coordinates while the physical/natural WM geometry is 720x1280 with a 270-degree rotation profile. The v54 platform bridge injects the already mapped logical display coordinates through `InputManagerGlobal.injectInputEvent()`.

Senderd reaches the persistent privileged bridge through the Linux abstract UNIX socket `arda_input_bridge`. No filesystem inode, app-data traversal, stale socket cleanup, or chmod step exists. SELinux permits `connectto` only from the dedicated `arda_vehicle_router` domain (plus controlled userdebug probe domains), and the bridge still verifies kernel peer credentials for the current root senderd runtime.

The old `app_process` and uinput paths remain explicit A/B fallbacks but are not the baseline.

### `video.first_frame_kick = false`

The old `center-cancel` experiment was an Android-12-era dirty-frame workaround. Its implementation was not a true CANCEL sequence; it could emit a DOWN-only pulse. The platform `screenrecord` backend does not use this hack in the baseline.

### Audio and sensors disabled

Audio remains disabled in the baseline. SensorSource and VHAL are also disabled by explicit master/destination gates, but the v55/v56 normalized sensor + Wasmtime policy configuration is present and ready for explicit A/B overrides.

Use `sensor-gate-smoke` and `sensor-wasm-smoke` before a real HU sensor session. See `ARDA_SENSOR_WASMTIME.md`.

## Candidates for later CLI cleanup

Do not remove these until the baseline is stable and the corresponding tests are archived:

- old private `libgui` native-display capture commands
- first-frame kick variants
- uinput as the default session injector
- legacy `aaos-aoa-gadget` bootstrap/install scripts
- duplicate aliases for Waveshare/display geometry flags

The cleanup rule is: move a working behavior into `config.toml`, verify it over repeated USB sessions, then remove stale aliases or probes one group at a time.

## One-command Mac workflow

The repository now includes:

```text
scripts/arda-usb-run.sh
```

From the repository root:

```bash
./scripts/arda-usb-run.sh
```

The script:

- optionally builds when `--build` is passed
- selects Pi serial `1000000028c0b59c` by default
- pushes `arda-senderd`
- pushes `config.toml` as `/data/local/tmp/arda-config.toml`
- checks/pushes `md_cert.pem` and `md_key.pem` from `~/Downloads/certs` when needed
- removes stale ARDA/screenrecord test processes
- runs the read-only `usb-accessory-status`
- starts `aap-run`

Use a second Mac terminal to start DHU over the Pi USB serial:

```bash
desktop-head-unit --usb=1000000028c0b59c
```

For a one-off override:

```bash
./scripts/arda-usb-run.sh -- --log-level summary
```

For build + push + run:

```bash
./scripts/arda-usb-run.sh --build
```
